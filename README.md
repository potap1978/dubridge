# dubridge

Превращает **веб-версию chat.deepseek.com** в помощника, умеющего работать с вашим локальным кодом.

Вы обычно общаетесь в веб-интерфейсе DeepSeek, а выводимые им инструкции-вызовы инструментов
перехватывает локальный Node-сервис, читает и пишет файлы, ищет по коду и выполняет команды
внутри заданной рабочей директории, а затем автоматически возвращает результат в поле чата —
образуется многораундовый замкнутый цикл «ИИ выдал инструкцию → локальное выполнение → результат
вернулся в диалог → ИИ продолжает».

- Не нужен API-ключ — используется ваша сессия в веб-версии.
- Не нужно расширение браузера и не нужно вставлять скрипты на страницу.
- Не читает и не использует ваши учётные данные.

---

## Как это работает

```
┌─ Chrome (запущен с --remote-debugging-port, отдельный каталог профиля) ──┐
│  вкладка chat.deepseek.com                                            │
│    ① внедрение хука: прозрачное разделение потока ответа fetch         │
│       (ReadableStream.tee)                                            │
│    ② передача: через Runtime.addBinding сырые фрагменты уходят в Node │
│    ③ возврат: Runtime.evaluate вызывает функцию страницы,              │
│       записывает в поле ввода и отправляет                            │
└──────────────────────────────┬────────────────────────────────────────┘
                               │ Chrome DevTools Protocol (Node → браузер)
┌──────────────────────────────▼────────────────────────────────────────┐
│ локальный сервис dubridge (Node.js + TypeScript)                       │
│  cdp/       обнаружение цели, присоединение к сессии, внедрение хука   │
│  stream/    разбор SSE → восстановление путей из патчей → терминал     │
│  protocol/  разбор вызовов инструментов, форматирование результатов    │
│  safety/    песочница путей, белый список команд и ручное подтверждение│
│  tools/     чтение/запись/правка/листинг/поиск/выполнение команд       │
│  loop/      ожидание ответа → разбор → выполнение → возврат → след. раунд│
└───────────────────────────────────────────────────────────────────────┘
```

Три проектных решения, о которых стоит сказать отдельно:

**1. Почему используется отладочный протокол, а не скрипт страницы, соединяющийся с локальным портом.**
JS на странице, пытающийся обратиться к `http://127.0.0.1:xxxx`, будет заблокирован CSP сайта
в директиве `connect-src`, к тому же при перезагрузке страницы внедрённый хук пропадёт.
При работе через отладочный протокол канал инициируется со стороны Node, а страница лишь
пассивно поставляет данные (вызов `addBinding` — это внутренняя пересылка браузера, а не
сетевой запрос), поэтому ни CSP не мешает, ни внедрённый хук не теряется — он автоматически
восстанавливается после перезагрузки страницы.

**2. Почему хук занимается только прозрачной пересылкой.**
Перехватив `window.fetch`, мы разделяем поток через `ReadableStream.tee()`: одна ветвь
без изменений отдаётся странице, другая читает исходные байты и отправляет их наверх.
Хук ничего не разбирает, не переписывает и не переупорядочивает; любое внутреннее
исключение возвращает исходный ответ. Даже если dubridge сломается — ваше ручное
использование DeepSeek не пострадает.

**3. Почему обязательно «восстановление путей из патчей», а не простая склейка строк.**
Потоковый ответ DeepSeek — это инструкции-патчи, поэтому приходится сначала поддерживать
модель документа сообщения, а уже потом извлекать из неё тело. В версии сайта от 2026-09
используются четыре типа кадров:

| Тип кадра | Пример | Смысл |
| --- | --- | --- |
| ① Полное состояние | `{"v":{"response":{"fragments":[…]}}}` | Только в начале потока — создаёт документ |
| ② Патч по пути | `{"p":"response/fragments/-1/content","v":"П"}`<br>`{"p":"response/status","o":"SET","v":"FINISHED"}` | Оператор `o` **часто отсутствует** |
| ③ Приращение значения | `{"v":"1"}` `{"v":"limit"}` | **Основная форма потоковой выдачи тела** — посимвольно складывается ответ |
| ④ Слияние полей | `{"updated_at":1789977769}` | Ключ самого кадра — это поле корневого объекта |

Три подводных камня, которые в своё время полностью ломали весь разбор:

- **Принять ③ за ①**: корневой объект снова и снова подменяется строками `"1"`, `"```"`,
  `fragments` теряется, тело всегда получается 0 символов. Теперь тип определяется
  **по форме самого значения** — если значение объект, это полное состояние; голая строка — всегда приращение тела.
- **Судить по «инициализирован ли документ»**: сайт перед ① посылает несколько кадров ④
  (`{"request_message_id":3}` и т.п.), и как только ④ создаст корень в виде `{}`, следующий
  за ним ① будет ошибочно принят за ③ и отброшен. Теперь ④, пока корень не создан, только
  **откладывается** и ни в коем случае не создаёт документ — дожидается ① и сливается с ним.
- **Пропустить или всегда считать `SET`, когда нет `o`**: пропуск — тело навсегда пустое;
  всегда `SET` — затирается предыдущее содержимое, начало ответа молча стирается.
  Теперь **тип выводится по типу цели и только в сторону «не потерять данные»**:

| Ситуация | Что выводится |
| --- | --- |
| Цель — строка, патч — строка | `APPEND` (склейка) |
| Цель — массив, патч — массив | Добавить элементы |
| Цель — скалярное поле (`status` / `quasi_status` / `message_id` / `type` / `role` — перечисления и идентификаторы) | `SET` (перезапись), чтобы не получить `WIPFINISHED` |
| Цель отсутствует | Создать |
| Типы не совпадают | Перезапись, но **с записью в предупреждения**, не молча |

Каждый вывод учитывается в статистике (в логе: `N применено / N выведено / N пропущено / N слито`),
чтобы потом можно было сверить. Принцип такой: пусть лучше склеится пара лишних символов и об этом
будет громко сказано, чем тихо получится неверный ответ.

У кадров-приращений тела нет пути — точка вставки задаётся `DUB_CONTENT_PATH`
(по умолчанию `response/fragments/-1/content`, где `-1` — последний фрагмент).
При следующих изменениях сайта править в первую очередь эту переменную.

## Быстрый старт

### 0. Требования

- Node.js **20.12+** (используется `process.loadEnvFile`)
- Chrome / Edge 116+
- Сетевое окружение, из которого доступен chat.deepseek.com

```bash
npm install
```

> Если в вашей конфигурации npm включено `omit=dev` (в некоторых корпоративных/CI окружениях
> это значение по умолчанию), dev-зависимости не установятся — тогда используйте
> `npm install --include=dev`.

#### Без установки: запуск через npx

Если вы просто хотите применить это к **своему текущему репозиторию**, не клонируя этот репозиторий,
можно запустить уже опубликованный пакет через npx:

```bash
npx dubridge --doctor                    # самопроверка (соответствует шагу 2)
npx dubridge                             # запустить сервис замкнутого цикла (шаг 3)
```

Запуск отладочного браузера — **это отдельный исполняемый файл**, а npx первым аргументом
ищет имя пакета в реестре, поэтому просто `npx dubridge-launch-chrome` не сработает
(он будет искать пакет с именем dubridge-launch-chrome). Указывайте имя пакета явно через `--package`:

```bash
npx --package dubridge dubridge-launch-chrome   # запустить отладочный браузер (шаг 1)
```

Тогда песочница рабочей директории и рабочий каталог команд по умолчанию берут **каталог,
в котором вы выполняете команду** — то есть тот репозиторий, над которым хотите работать;
`agent.md` тоже читается из этого каталога.

С промптом наоборот: сначала берётся `prompts/deepseek-system-prompt.md` из вашего текущего
каталога, а **если не найден — используется встроенный в пакет**, так что для сценария npx
ничего готовить не нужно. Хотите свой — положите файл с тем же именем в текущий каталог.

> О кэше npx: npm иногда переиспользует старую версию; чтобы гарантированно получить свежую,
> используйте `npx dubridge@latest`.

### 1. Запуск сервиса (одной командой)

```bash
npm start
```

**По умолчанию сначала идёт предполётная проверка, затем сервис** — три шага идут автоматически:

1. **Убедиться, что отладочный порт готов** — если нет, автоматически поднять отдельный
   отладочный браузер (автоопределение Chrome/Edge, отдельный профиль
   `dubridge-chrome-profile` во временной директории системы, отладочный порт 9222 слушает
   только loopback);
2. **Дождаться целевой вкладки** — до 30 секунд, чтобы вы успели открыть и войти
   в <https://chat.deepseek.com> во всплывшем окне;
3. **Самопроверка** — по порядку: конфиг → отладочный порт → целевая вкладка → подключение по CDP
   → внедрение хука → доступность поля ввода и кнопки отправки.

**При провале любого шага запуск прерывается и печатается причина**, а не оставляет сервис
крутиться в сломанном окружении (поднявшись, он привяжется и будет ждать 180 секунд —
вы увидите «зависание» и не поймёте: браузер не запущен или вы не вошли). Например:

```text
ERR [dubridge] Предполётная проверка не пройдена, запуск прерван {"причина":"no-target"}

Уже 30 секунд не обнаружена вкладка https://chat.deepseek.com. Откройте её
в отладочном браузере и войдите, затем повторите попытку.

ERR [dubridge] Чтобы пропустить предполётную проверку и запустить сервис сразу, используйте:
npm start -- --no-preflight
```

> Почему обязательно отдельный каталог конфигурации: отладочный порт передаёт полный контроль
> над браузером любому локальному процессу, поэтому отдельный экземпляр сужает поверхность
> риска до специально выделенного браузера и не затрагивает сессию и cookie вашего повседневного браузера.

**Запустить отдельный шаг** (полезно при отладке):

```bash
npm run launch-chrome           # только запустить отладочный браузер
npm run launch-chrome -- --dry-run   # только посмотреть, какая команда будет выполнена
npm run doctor                  # только самопроверка, без правок страницы и вызова инструментов
npm start -- --no-preflight     # пропустить предполётную проверку и сразу поднять сервис
```

### 2. Промпт отправляется автоматически

При запуске сервис **сам** отправит текст между разделителями из
`prompts/deepseek-system-prompt.md` в текущий диалог — вручную копировать не нужно.

Два ограничения:

- **Только в пустой диалог**. Как только сайт начинает сессию, URL становится
  `/a/chat/s/<id>`, и по умолчанию отправка пропускается — чтобы каждый перезапуск не
  вставлял длинное сообщение в ваш идущий диалог. Принудительно: `npm start -- --send-prompt`;
  полностью отключить: `npm start -- --no-prompt` или `DUB_AUTO_SEND_PROMPT=false`.
- **После отправки следующий раунд вызова инструментов пропускается**. Ответ модели на сам
  промпт может скопировать блок `tool_call` из примера — это не настоящая инструкция, и её
  выполнение было бы ошибкой.

В терминале чётко видно результат:

```
INF [dubridge:bootstrap] Промпт загружен {"файл":"prompts/deepseek-system-prompt.md","способ извлечения":"взять текст между разделителями","символов":4102}
INF [dubridge:bootstrap] Обнаружен пустой диалог, готовим отправку промпта {"основание":"сейчас на главной, беседа ещё не начата"}
INF [dubridge:bootstrap] Промпт отправлен, следующий раунд пропустит выполнение инструментов (чтобы модель не скопировала tool_call из примера)
INF [dubridge:loop] Этот ответ пришёл от самопроверки промпта, выполнение инструментов пропущено
```

Хотите поменять содержимое промпта — правьте `prompts/deepseek-system-prompt.md`
(пояснения для людей можно писать за пределами разделителей, они не отправляются).
`npm run doctor` дополнительно сообщает, пуст ли текущий диалог — удобно понять, ушёл промпт или нет.

**Раздел `## Инструменты и параметры` — генерируемый**: содержимое между `<!-- tools:begin -->` и
`<!-- tools:end -->` берётся из `promptGuidelines` в определениях инструментов
(`src/tools/*.ts`); после правки инструментов синхронизируйте через `npm run gen:prompt`.
`npm test` сверяет этот фрагмент файла с сгенерированным — если поменяли схему и забыли
синхронизировать, тест сразу упадёт, а не будет ждать ошибок с прежними аргументами.

**Проектные соглашения (`agent.md`) автоматически дописываются после промпта и отправляются вместе.**
Общий промпт рассказывает «как пользоваться инструментами», а стек, доступные команды
и жёсткие ограничения у **каждого проекта свои**, поэтому они выносятся в отдельный `agent.md`
в рабочей директории:

- Содержимое **прикрепляется как есть** (без вырезания по разделителям) и в тексте явно
  помечено «при конфликтах приоритет у этого раздела»;
- Если файла нет — **молча пропускается**, отправляется только общий промпт (он изначально опционален);
- Намеренно **не разбирается `package.json`**: рабочая директория не обязательно Node-проект,
  а формат файла соглашений не зависит от языка;
- Свыше 20000 символов — обрезается с пометкой об обрезке;
- Другой путь — через `DUB_AGENT_FILE`; пустое значение = не прикреплять.

`npm run doctor` сообщает, найден ли файл соглашений. В логе запуска тоже видно, сколько символов ушло:

```
INF [dubridge:bootstrap] Промпт загружен {"файл":"prompts/deepseek-system-prompt.md","способ извлечения":"взять текст между разделителями","символов":4102}
INF [dubridge:bootstrap] Проектные соглашения прикреплены {"файл":"agent.md","символов":2183,"обрезано":false}
INF [dubridge:bootstrap] Промпт отправлен, следующий раунд пропустит выполнение инструментов
```

### 3. Веб-панель статистики

После запуска сервиса в правом верхнем углу страницы DeepSeek появляется небольшой
постоянный блок, показывающий в реальном времени:

- **Суммарный оборот ≈**: суммарное число символов тела «отправлено + получено» как
  ориентир по объёму (это не токены и не текущая занятость контекстного окна сайта — только растёт);
- **Сообщений отправлено, раундов N**: сколько сообщений реально отправлено (сообщения
  пользователя + возвращённые результаты инструментов);
- **Вызовов инструментов, раундов N**: сколько раундов с выполнением инструментов (в одном раунде может быть несколько вызовов);
- **Строка состояния внизу**: во время выполнения инструментов и возврата результата — вращающийся
  ключ (сначала «🔧 Выполняется xxx…», затем в фазе возврата «🔧 Отправка результата…»), по завершении скрывается.

Данные панели считает Node и передаёт на страницу по CDP, страница только рендерит.
Сбой передачи не влияет на основной процесс.

Панель закреплена в правом верхнем углу; после перезагрузки страницы она появляется
за счёт «одноразовой отправки при подключении» — ждать следующего обмена не нужно.

### 4. Начинайте пользоваться

Просто давайте указания, например:

> Сначала list_dir по корню, потом read_file для package.json, скажи как этот проект запускать.

DeepSeek выводит блок `tool_call` → выполняется локально → результат автоматически
возвращается в диалог → он продолжает. Когда он больше не выводит вызовы инструментов — раунд закончен.

## Конфигурация

Скопируйте `.env.example` в `.env` и по необходимости правьте. Часто используемые:

| Переменная | По умолчанию | Описание |
| --- | --- | --- |
| `DUB_CDP_PORT` | `9222` | Отладочный порт, должен совпадать с запуском Chrome |
| `DUB_WORKSPACE_ROOT` | каталог запуска | **Корень песочницы файловых операций**; пусто = рабочая директория запуска сервиса |
| `DUB_COMMAND_WHITELIST` | встроенный консервативный список | Белый список команд, через запятую, по префиксу |
| `DUB_AUTO_APPROVE_COMMANDS` | `false` | `true` = пропустить ручное подтверждение (высокий риск, см. ниже) |
| `DUB_RESPECT_GITIGNORE` | `true` | Учитывать ли `.gitignore` при поиске и листинге (включая вложенные и `!`); `false` = пропускать только встроенные тяжёлые каталоги |
| `DUB_READ_ONLY` | `false` | `true` = режим только чтения: доступны только `read_file` / `list_dir` / `search`, запись и выполнение команд целиком исключены |
| `DUB_MAX_FILE_BYTES` | `262144` | Лимит одного чтения, излишек обрезается с пометкой |
| `DUB_MAX_RESULT_CHARS` | `16384` | Лимит возврата одного результата |
| `DUB_MAX_COMMAND_OUTPUT_CHARS` | `16384` | Лимит тела вывода команды; при превышении сохраняется конец, а шапка (команда, решение, код возврата) сохраняется всегда |
| `DUB_SEND_MIN_INTERVAL_MS` | `3000` | Минимальный интервал между отправками, снижает риск антифрода |
| `DUB_REPLY_MIN_GAP_MS` | `2000` | Минимальный интервал «ответ получен → возврат и отправка»; если инструменты сработали быстрее — добираем паузу |
| `DUB_FILL_WAIT_MS` | `5000` | Лимит ожидания пустого поля ввода перед возвратом; при таймауте отложить и показать подсказку «отправить повторно» |
| `DUB_STREAM_CONFIRM_MS` | `8000` | Окно подтверждения «сайт начал генерацию»; если не дождались — только предупреждение в логе, без повторной отправки. `0` = выключено |
| `DUB_RESPONSE_TIMEOUT_MS` | `180000` | Таймаут ожидания полного ответа |
| `DUB_MAX_REPEAT_CALLS` | `3` | Сколько подряд идущих одинаковых вызовов считать «топтанием на месте» |
| `DUB_API_PATH_PATTERN` | `/api/v0/chat/completion` | Подстрока URL эндпоинта ответа; правится при изменениях сайта |
| `DUB_CONTENT_PATH` | `response/fragments/-1/content` | Путь точки вставки тела (у кадров-приращений тела пути нет) |
| `DUB_AUTO_SEND_PROMPT` | `true` | Автоотправка промпта при запуске (только в пустом диалоге) |
| `DUB_PROMPT_FILE` | `prompts/deepseek-system-prompt.md` | Файл промпта; отправляется только текст между первой парой `---` |
| `DUB_AGENT_FILE` | `agent.md` | Файл проектных соглашений; дописывается после промпта, пусто = не прикреплять |

Все файловые операции ограничены `DUB_WORKSPACE_ROOT`. Хотите, чтобы работал
с конкретным проектом — просто укажите его:

```env
DUB_WORKSPACE_ROOT=D:/code/my-project
```

## Инструменты и границы безопасности

| Инструмент | Назначение | Уровень риска |
| --- | --- | --- |
| `read_file` | Чтение текстовых файлов (тело как есть, без нумерации строк; поддерживает диапазон и продолжение; не-UTF-8 кодировки распознаются и помечаются) | только чтение |
| `list_dir` | Листинг каталога (пропускает `node_modules`, `.git` и прочие тяжёлые каталоги и содержимое из `.gitignore`) | только чтение |
| `search` | Поиск по содержимому или по имени файла; `glob` (`*.ts`, `src/**/*.ts`), `context` — строки контекста, учитывает `.gitignore` | только чтение |
| `write_file` | Запись/перезапись файла (новые всегда в UTF-8; перезапись не-UTF-8 файла отклоняется) | запись |
| `edit_file` | Замена по фрагменту оригинала, за раз можно несколько блоков (игнорируются CRLF/LF и хвостовые пробелы; при записи сохраняются исходные переводы строк и BOM; только UTF-8) | запись |
| `run_command` | Выполнение команд терминала (при необходимости — диалог подтверждения на странице, при недоступности — в терминале сервиса) | выполнение |

**Режим только чтения** (`DUB_READ_ONLY=true`) оставляет только три читающих инструмента;
`write_file` / `edit_file` / `run_command` **удалены из списка инструментов**, а не блокируются
при вызове — их нет в списке, значит нет и в промпте. Если всё же будут вызваны — вернётся
`TOOL_DISABLED` с перечнем доступных. Специально **не предусмотрены «только читающие команды»**:
у `cat` и `node -e` по строке команды невозможно определить «только читающая она или нет»;
чем гадать, лучше исключить весь класс.

**Ctrl+C завершает выполняющуюся команду.** По сигналу выхода сначала посылается сигнал остановки,
затем идёт завершение: `run_command` завершает всё дерево процессов (`taskkill /T /F` на Windows,
kill группы процессов на Unix-подобных), в результат честно пишется «прервано» с выводом,
полученным до прерывания. Иначе длинная сборка с таймаутом 120 секунд подвесила бы выход
и оставила полузапущенные сервисы с занятыми портами.

### Где происходит обрезка и опущение

Когда содержимое превышает лимит, **какой конец сохраняется — определяет форма содержимого**:

- **У вывода команды сохраняется хвост**: ошибки, итоги тестов, вывод сборки — в последних
  строках, сохранение головы как раз потеряло бы вывод. Буферный слой (4MB) и слой возврата
  отбрасывают «самые ранние байты/символы» и в начале текста пишут, сколько опущено;
  шапка (команда, решение, код возврата, время) сохраняется полностью — даже при обрезке тела
  видно, чей это вывод.
- **Файлы, результаты поиска, листинг каталога — сохраняется голова**: начало это точка входа,
  читать дальше всё ещё можно.

В месте опущения всегда пишется «сколько опущено и с какого конца», на ярлыке результата
тоже отмечается `обрезано (сохранён конец)`, чтобы половину вывода не приняли за полный.

### Текст результата и структурированная сводка

У каждого результата инструмента две стороны:

- **Тело (`data`) для модели**: в чат возвращается только тело, формат — «текст, понятный с одного взгляда»;
- **Структурированная сводка (`structured`) для программы**: попадания, статистика сканирования,
  диапазоны строк, кодировка, код возврата и прочая учётная информация — отдельными полями,
  только в лог и программным потребителям (если в будущем появится внешний API — не придётся
  разбирать текст обратно).

Обе стороны генерируются инструментом из **одних и тех же данных**, поэтому «в тексте одно число,
в полях другое» невозможно. Сводка намеренно **не возвращается в чат**: модели нужно только
читаемое тело, добавлять второй JSON — шум. Пропущенные элементы тоже учитываются
(пропущено бинарных, пропущено по `.gitignore`, отфильтровано по glob) — чтобы «не нашлось»
и «вообще не искали» не смешивались.

### Кодировки текста

При чтении кодировка определяется по порядку, и каждый шаг намеренно консервативен —
UTF-8 файл не будет ошибочно распознан как что-то другое:

1. **BOM**: UTF-8, UTF-16 LE/BE принимаются сразу (UTF-16 с BOM не будет ошибочно принят за бинарный по NUL);
2. **Строгий UTF-8**: если валиден — используется без догадок;
3. **Строгий GB18030**: принимается, только если результат «похож на китайский текст»
   (нет управляющих символов, есть хотя бы один иероглиф).

Не-UTF-8 файлы **читаются и ищутся, но не перезаписываются**:

- `read_file` в шапке указывает «Кодировка: GB18030»; `search` как обычно находит и в
  статистике пишет «декодировано N по не-UTF-8» — раньше такие файлы молча считались бинарными;
- `edit_file` и `write_file` при перезаписи существующего файла вернут `UNSUPPORTED_ENCODING`
  с объяснением причины. Дело в том, что в Node встроен только UTF-8-энкодер; для записи
  в исходной кодировке пришлось бы тянуть зависимость типа iconv; и что важнее — тихая подмена
  всей кодировки файла сделает git diff полностью красным, а внешние инструменты не смогут
  прочитать файл. Единственный путь: сохранить в редакторе как UTF-8.

Что намеренно не делается: UTF-16 без BOM (без BOM его трудно отличить от бинарного),
Big5 / Shift-JIS и прочие многобайтные кодировки (дальше угадывать — только расширять область ошибок).

### Учёт .gitignore

`search` и `list_dir` по умолчанию учитывают `.gitignore` в `DUB_WORKSPACE_ROOT`
(`DUB_RESPECT_GITIGNORE=false` отключает): читается `.gitignore` корня и вложенных каталогов по пути,
поддерживаются комментарии, `!`-исключения, анкор `/` в начале, `/` в конце — только каталоги,
`*` / `**` / `?` / `[abc]`; чем глубже вложено правило, тем выше приоритет. В результате
пишется «пропущено N по .gitignore».

Что намеренно не делается: `.git/info/exclude`, глобальный `core.excludesFile`, подмодули.
Цепочка предков начинается с рабочей директории: если `DUB_WORKSPACE_ROOT` указывает на подкаталог
репозитория, корневой `.gitignore` репозитория не будет прочитан (файлы за пределами рабочей
директории не читаются — это красная линия песочницы).

`glob` в поиске тоже ограничен этим уровнем синтаксиса: `*` не пересекает `/`, `**` пересекает,
`?` — один символ, `[abc]` — класс, развёртывание фигурных скобок не поддерживается.
Шаблон без `/` совпадает как «имя файла на любом уровне» (`*.ts` эквивалентно `**/*.ts`).

### Песочница путей

Две проверки, обе обязательны:

1. **Лексическая**: после `path.resolve` — внутри ли рабочей директории; отсекает `..` и абсолютные пути;
2. **Проверка реального пути**: `realpath` ближайшего существующего предка — отсекает симлинки и junction'ы.

Выход за пределы всегда **отклоняется с возвратом кода ошибки**, без тихой подмены на путь внутри
рабочей директории — тихая подмена создала бы иллюзию успеха, хотя на деле правка ушла не туда.

### Решение по командам

Три исхода:

- **auto**: попадание в белый список, выполнить сразу.
- **confirm**: нужно ручное подтверждение. **Приоритетно — диалог подтверждения на странице
  DeepSeek** («Разрешить» / «Отклонить»); если страница недоступна (хук не внедрён, CDP оборван) —
  откат к вводу `y` в терминале сервиса. Сюда входят: команды вне белого списка, команды с `&&`,
  `|`, `;`, `>` и другими склейками, длительно живущие команды (`npm run dev` и т.п.), а также
  высокорисковые фрагменты `rm` / `git push` / `npm publish` / повышение прав.
- **deny**: катастрофические шаблоны (`rm -rf /`, форматирование диска, выключение ПК,
  удаление ветки реестра…) — **не выполняются ни при какой конфигурации**.

Порядок проверки намеренно ставит «склейки» перед белым списком: первое слово у
`npm run build && rm -rf .` попадает в белый список, но семантика всей строки давно вышла за рамки списка.

Ещё две страховки:

- **Провал подтверждения на странице → откат в терминал; недоступно и там — отказ.**
  Подтверждение через страницу требует внедрённого хука и присоединённой страницы; если этот
  путь недоступен, автоматический откат в терминал сервиса. Если и терминал не интерактивный
  (запущен из скрипта или CI, где ответить `y/n` некому) — по умолчанию «отказ», а не «пропустить».
- **Встроенный белый список намеренно консервативен**: только читающие запросы и команды сборки/
  проверки внутри проекта, без интерпретаторов типа `node`, `python`, позволяющих выполнить
  произвольное выражение (`node -e "..."` — это произвольное исполнение кода). Нужно больше — допишите сами в `.env`.

### Защита от разбега замкнутого цикла

- Не более **30** раундов возврата в одной сессии; при превышении автовозврат останавливается и предлагается ручное вмешательство;
- Одна и та же группа вызовов **подряд** больше `DUB_MAX_REPEAT_CALLS` (по умолчанию 3) раундов — прерывание.
  Счётчик признаёт только «подряд»: если вызов не появился в предыдущем раунде — обнуляется;
  и как только успешно выполнился `write_file`/`edit_file`, весь счётчик обнуляется —
  «изменил код и снова запустил ту же команду» это нормальный процесс, а не бесконечный цикл;
- Провал возврата, провал разбора — всегда **сообщается в диалог**, без тихих повторных попыток:
  отправка имеет побочные эффекты, повтор может привести к повторной записи или повторному выполнению.

## Решение проблем

| Симптом | Причина и что делать |
| --- | --- |
| `Не удалось найти отладочный порт Chrome на http://127.0.0.1:9222` | Браузер не запущен с отладочным портом или порт другой. Запустите `npm run launch-chrome` |
| `Не обнаружена вкладка, начинающаяся с https://chat.deepseek.com` | Откройте DeepSeek в отладочном браузере и войдите |
| Хук не работает / объект внедрения не читается | Возможно, страница только что перезагрузилась; подождите или перезапустите `npm run doctor` — doctor выведет текущие кандидаты селекторов и структуру кадров |
| Ответ приходит, но команды не выполняются | Проверьте, выводит ли DeepSeek блок `tool_call` согласно промпту (информационная строка обязательно `tool_call`); обычный блок ```json не считается инструкцией |
| Ответ пришёл, но «символов: 0» | Возможно, протокол сайта опять изменился. В этом случае сервис **сам печатает в терминал первые и последние кадры потока** — приложите этот вывод и можно локализовать; статистика `N кадров / N выведено / N пропущено / N слито` тоже в логе |
| Лог говорит «только мысли (THINK-фрагмент)» | В этом раунде модель выдала лишь процесс размышления без тела (вызовы из размышлений не считаются инструкцией). Переформулируйте вопрос или попросите сразу выдать вывод |
| Сбой возврата: не найдено поле ввода чата | Изменения сайта сделали селектор недействительным. `npm run doctor` перечислит количество совпадений и видимость всех кандидатов |
| Сбой возврата: считанное после записи не совпадает | В деталях указаны ожидаемая/фактическая длина, позиция первого различия и фрагменты с обеих сторон; «различие только в пробелах или переводах строк» обычно означает, что запись в основном удалась, а редактор нормализовал вёрстку — по этому можно решить, нужно ли менять возвращаемое содержимое |
| В логе «не наблюдалось начало генерации сайтом» | После возврата сайт не открыл новый поток ответа, значит, отправка, скорее всего, не принята. Посмотрите в чат: если содержимое ещё в поле — нажмите Enter; если поле пустое и сообщения в чате нет — сайт проглотил отправку. Окно подтверждения настраивается через `DUB_STREAM_CONFIRM_MS` (`0` = выключено) |
| Поле ввода непустое, возврат постоянно ждёт | Если это содержимое — результат инструмента, не отправленный в прошлом раунде, хук сам опознает и досылает один раз; если это ваш набранный черновик — появится подсказка и вы решаете, никогда не перезаписывается |
| При холодном старте промпт не отправлен | Сервис сначала ждёт готовности страницы, потом судит о пустоте диалога; если в логе «не удалось найти поле ввода», обычно страница не загрузилась или нет входа — подождите и перезапустите |
| Получено «терминальное состояние сайта: содержимое заблокировано / контекст переполнен» | Это нормальное ограничение DeepSeek, а не проблема dubridge; в диалоге это явно помечено, чтобы половину ответа не принять за полный |
| Команды всегда отклоняются | Нет ни диалога подтверждения на странице, ни интерактивного терминала. Проверьте, работает ли хук страницы (`npm run doctor`); либо запускайте `npm start` в переднем плане терминала, либо добавьте команду в `DUB_COMMAND_WHITELIST` |
| Краказябры в выводе китайских команд | На Windows автоматически переключается кодовая страница на UTF-8; если всё равно аномально, обычно это кодировка самой вызываемой программы |
| `edit_file` / `write_file` возвращает `UNSUPPORTED_ENCODING` | Цель — не UTF-8 (GB18030, UTF-16, бинарный или нераспознанная кодировка). Это **намеренный отказ**: запись заменила бы весь файл на UTF-8. Сохраните в редакторе как UTF-8 и правьте, или удалите и создайте заново; чтение и поиск не затрагиваются |
| Промпт не отправлен автоматически | Текущий диалог не пустой (URL `/a/chat/s/<id>`). Для принудительной отправки в текущий диалог: `npm start -- --send-prompt`; чтобы ушло в новый — вернитесь на главную сайта и запустите снова |
| Промпт ушёл, но модель не вызывает инструменты в нужном формате | Сначала `npm run doctor` — читается ли файл промпта; затем проверьте, есть ли в файле `DUB_PROMPT_FILE` парные разделители `---` |

## Предупреждение о рисках

Оцените честно, прежде чем использовать:

1. **Антифрод аккаунта**: автоматизация веб-чата может запускать антифрод и капчу сайта,
   а также может нарушать условия обслуживания сайта. Минимальные интервалы отправки и
   последовательная очередь уже встроены, но не стоит использовать в высоком темпе.
   При появлении капчи инструмент **только предлагает пройти её вручную, никак не обходит**.
2. **Выполнение команд — самая рискованная поверхность**: стратегия по умолчанию
   «белый список автоматически + остальное вручную». `DUB_AUTO_APPROVE_COMMANDS=true` позволит ИИ
   работать с вашим компьютером без подтверждения — включайте только с полным пониманием последствий.
   Если хочется, чтобы только читал код — используйте `DUB_READ_ONLY=true`: запись и выполнение
   команд просто не входят в набор инструментов.
3. **Отладочный порт — вход с высокими правами**: инструмент слушает только loopback и использует
   отдельный экземпляр браузера. Не входите в важные аккаунты в браузере с отладочным портом,
   закрывайте этот экземпляр по завершении.
4. **Ноль касаний учётных данных**: инструмент не читает токены аутентификации из `localStorage`,
   логи тоже маскируются (`token`/`cookie`/`authorization` и т.п. заменяются на `[redacted]`).
5. **Изменения сайта ломают работу**: основные точки отказа — структура путей патчей и селекторы
   поля ввода. `npm run doctor` выводит актуально наблюдаемую структуру, что помогает быстро
   локализовать проблему; `DUB_API_PATH_PATTERN` позволяет подправить правило сопоставления API
   без изменения кода.

## Лицензия

Только для локальной персональной автоматизации.
